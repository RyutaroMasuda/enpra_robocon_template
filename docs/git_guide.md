# Git 運用ガイド

ロボコン期間は約2ヶ月と短く、4人前後で 機構 / 回路 / 制御 を同時に進めます。
「誰がいつ何を変えたか」「本番で動いたのはどれか」がすぐ分かる状態を保つのが目的です。

---

## 1. 基本の流れ

```
main ─────●─────────────●──────────●──── (いつでも動く状態)
           \           /          /
            ●──●──●───┘  feature/drive-pid
                       \
                        ●──●─────┘  fix/can-timeout
```

1. `main` から作業用ブランチを切る
2. 作業してこまめにコミット
3. GitHubで Pull Request (PR) を出す
4. もう1人が確認して `main` にマージ
5. 作業ブランチは削除

```bash
git switch main
git pull                          # 作業前に必ず最新にする
git switch -c feature/<内容>       # ブランチを作る
# ... 作業 ...
git add <変更したファイル>
git commit -m "feat: <何をしたか>"
git push -u origin feature/<内容>
# → GitHubでPRを作る
```

## 2. ブランチのルール

| ブランチ | 用途 | 例 |
|---|---|---|
| `main` | **実機で動作確認できたもの**だけ。直接pushしない | |
| `feature/<内容>` | 新しい機能 | `feature/drive-control` |
| `fix/<内容>` | バグ修正 | `fix/servo-angle` |
| `exp/<内容>` | 実験・ボツになるかもしれないもの | `exp/new-mechanism` |

- GitHubの Settings → Branches で `main` を保護（直接pushを禁止）しておくと事故が減ります。
- 大会直前は特に、`main` = 「最後に動いた状態」を守ること。

## 3. コミットのルール

- **1コミット = 1つの変更**。「いろいろ修正」はNG
- メッセージは `種類: 内容` の形にする

| 種類 | 意味 |
|---|---|
| `feat` | 機能追加 |
| `fix` | バグ修正 |
| `docs` | READMEやドキュメントだけの変更 |
| `refactor` | 動作は変えずに整理 |
| `test` | 動作確認用の変更 |
| `cad` / `pcb` | 設計データの更新 |

```
feat: 足回りの速度指令を追加
fix: 通信が途切れたときにモータを止める
cad: 上物フレームの穴位置を修正 (v2)
pcb: 基板ver2 発注データ
```

## 4. タグとリリース：「本番で使ったもの」を残す

大会・試走会など **節目で動いた状態にはタグを打つ**。後輩が「本番の状態」をすぐ再現できます。

```bash
git tag -a v1.0-honban -m "本番で使用したバージョン"
git push origin v1.0-honban
```

- 基板の発注データ（ガーバーzip）は、リポジトリに毎回コミットするより
  **GitHub Releases に添付**すると履歴がきれいになります。
- 「Honban_code_1」のようにリポジトリ名で本番を表すのではなく、**タグで表す**のがおすすめ。

## 5. Issue でタスク管理

- やること・不具合は Issue に書く（`.github/ISSUE_TEMPLATE` が使える）
- PRの説明に `closes #12` と書くと、マージ時にIssueが自動で閉じる
- GitHub Projects（カンバン）でチームの進捗を見える化すると、カレンダー管理も楽

## 6. CAD・基板などバイナリファイルの注意

SolidWorks や KiCad の一部ファイルは **2人が同時に編集するとマージできません**。

- 編集前に「このファイル触ります」とIssueやチャットで宣言する
- 可能なら Git LFS の lock 機能を使う（`git lfs lock <file>`）
- 部品はユニットごとにフォルダを分け、担当者を決める
- 大きいファイル（100MB超）はGitHubにpushできない → Git LFS を使う

## 7. やってはいけないこと（先輩チームで実際に起きたこと）

| NG | 理由 / 対策 |
|---|---|
| 自動バックアップ（`*-backups/*.zip`）をコミット | 同じデータが何十個も入り容量が膨れる。履歴はGitが持っているので不要 → `.gitignore` |
| ロック・一時ファイル（`~$xxx`, `*.lck`, `_autosave-*`）をコミット | 他の人の環境で邪魔になる → `.gitignore` |
| 動作確認のたびに新しいリポジトリを作る | 40個近くに増えて見にくくなり、結局privateにした → `experiments/` に1フォルダずつ |
| `新しいフォルダー`、`Part1`、`WORK` のような名前 | 何のファイルか誰も分からない → [命名規則](naming_rules.md) |
| `xxx_ver1`, `xxx_ver2` とファイルを複製 | バージョン管理はGitの仕事。ファイルは1つにして履歴で管理 |
| パスワード・個人のメールアドレス・コントローラのMACアドレスをコードに直書きしてpublicに | 設定は別ファイルにして `.gitignore` するか、privateリポにする |
| `git add .` で何でも入れる | `git status` で何が入るか確認してからコミット |

## 8. 困ったとき

```bash
git status                 # 今の状態を確認（迷ったらまずこれ）
git log --oneline --graph  # 履歴を見る
git diff                   # まだコミットしていない変更を見る
git restore <file>         # コミット前の変更を取り消す
git switch -c rescue       # 変な状態になったら、とりあえず別ブランチに逃がす
```

- `git push --force` と `git reset --hard` は、意味が分かるまで使わない
- コンフリクトしたら一人で抱えず、相手と画面を見ながら解決する
