# リポジトリ構成の考え方

## 先輩チーム（2024 A班）の構成

| リポジトリ | 中身 |
|---|---|
| `README` | organizationの説明・組織図・システム図・カレンダー |
| `Honban_code_1` | 本番の制御コード（マイコンごとにフォルダ） |
| `ESP32_WROOM32E_PCB_mr` | 基板データ（KiCad）と発注データ |
| `ROBOT_CAD` | 機構設計データ（SolidWorks） |
| `Mecanum_Encoder`, `CAN` | 動作確認用コード |

「**制御・基板・CADの3つがあれば本番機体を作れる**」という分け方はとても良かった点です。
このテンプレートもこの分け方を引き継いでいます。

## 改善した点

### 1. organizationのトップページは `.github` リポジトリで作る
`README` という名前のリポジトリではなく、`.github` リポジトリの `profile/README.md` に書くと、
organizationのトップページに直接表示されます。さらに `.github` に置いた Issue / PR テンプレートは
**全リポジトリ共通**で使えます。

### 2. 動作確認コードは `experiments` 1つにまとめる
先輩チームでは動作確認のたびにリポジトリを作り、約40個に増えてしまいました。
`experiments/` の中に `日付_内容_名前/` というフォルダを作るようにすれば、
1か所で見渡せて、後から「あの実験どこだっけ」となりません。

### 3. 本番版はリポジトリ名ではなく「タグ」で示す
`Honban_code_1` → `firmware` リポジトリに `v1.0-honban` のタグを打つ。
試走会・本番など、動いた状態をいくつでも残せます。

### 4. 自動生成ファイルを `.gitignore` で最初から除外
KiCadのバックアップzip、SolidWorksの `~$` 一時ファイル、ロックファイルなどは、
最初に `.gitignore` を置いておけば混ざりません。

### 5. CADは「アセンブリ / 自作部品 / 市販品 / 出力ファイル」に分ける
ルート直下に部品が散らばっていると、どれが最新でどれが使われているか分かりません。
役割ごとにフォルダを分け、**開くべきアセンブリをREADMEに明記**します。

## リポジトリを増やしたくなったら

基本は5つで足ります。増やしてよいのは次のような場合だけにしましょう。

- 全く別のマイコン・言語・ツールで、ビルド方法が違う（例：PC側のアプリ）
- 公開範囲を変えたい（一部だけprivateにしたい）

「ちょっと試したい」は `experiments/` か、`exp/xxx` ブランチで。
